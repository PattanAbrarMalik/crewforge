# Be ready to explain the system

1. **Why is a last-seat race safe?** A count read in JavaScript is not the lock. The membership INSERT executes a database trigger that checks current capacity inside the same serialized write transaction. The subsequent trigger updates the count. Competing inserts cannot both commit the final seat.
2. **Why not just use an in-memory mutex?** A mutex in one Worker isolate would not coordinate other isolates or survive restarts. The database is the shared consistency boundary.
3. **Why are authorization checks repeated?** A leader may leave between the initial HTTP lookup and the write. The guarded statement inside the atomic batch checks the current leader again. A failed check rolls back the receipt, mutation and audit entry.
4. **What does idempotency actually guarantee?** A committed actor/key receipt returns its original response. A different payload under that key conflicts. Failed transactions leave no success receipt. Rate limiting may still reject an excessive retry burst before commit; once the receipt exists, replay occurs before rate limiting.
5. **What happens when the leader leaves?** The delete trigger decrements the count and chooses the oldest remaining member, with user ID breaking timestamp ties. The final member's departure deletes the team. Audit rows intentionally have no cascading team foreign key, so history survives.
6. **Are realtime messages the source of truth?** No. SSE sends audit revision IDs; database reads return the state. Clients reconnect and refresh. Intermediate revision events may coalesce, while the durable audit retains the actual changes.
7. **What is cached?** Only a pending identical board query can be shared; there is no timer-based stale cache. Mutations invalidate event-scoped sharing. If the initiating request is interrupted, a dependent reader retries in its own request context. Matching and authorization decisions never use this read-sharing map.
8. **What do the numbers prove?** The 50-way race test exercises the real API and SQLite. The load report measures loopback HTTP through workerd with a synthetic 10k/2k dataset. It does not measure public TLS/network latency. The chaos result proves local committed-but-unacknowledged recovery, not every type of cloud failure.
9. **What are the tradeoffs?** D1 serializes writers, so sustained write throughput is bounded. SSE polls every 1.5 seconds. Keyword search uses token prefixes, not arbitrary substring or semantic search. Broad search under concurrency can be slower than the default board. Matching averages team UTC offsets and uses skills; it is deliberately explainable but cannot judge interpersonal fit.
10. **What would you improve next?** Measure the hosted deployment from multiple regions; introduce dedicated read models if real query traffic warrants them; add event administration and controlled audit retention policies; improve timezone availability modeling using actual working windows. Do not claim these extensions already exist.
